DACL INJECTION SEQUENCE — HOW THE ATTACK WORKS
=============================================================================

Each injection fires in two stages per Token handle:

STAGE 1 (T+0ms): Inject S-1-0-xxx as first ACE — GenericAll access
  OldSd: D:(A;;GA;;;lloyd)(A;;GA;;;SY)(A;;GXGR;;;S-1-5-5-0-SESSION)
  NewSd: D:(A;;GA;;;S-1-0-xxx)(A;;RC;;;OW)(A;;GA;;;lloyd)(A;;GA;;;SY)
          ^^^^^^^^ GHOST SID ADDED FIRST — gets GenericAll

                                                              ^^^^^^ SESSION SID GONE

STAGE 2 (T+92ms): Ghost SID also stripped — evidence cleanup
  NewSd: D:(A;;GA;;;lloyd)(A;;GA;;;SY)
  [Session SID permanently removed. Ghost SID window = ~92ms]

Effect: The S-1-0-xxx entity had a ~92ms window with FULL ACCESS (GenericAll)
to lloyd's token — enough to duplicate/impersonate the token.

THE S-1-0-xxx SIDS: WHAT ARE THEY?
=============================================================================

S-1-0 = NULL SID authority (identifier authority 0). No legitimate Windows
service or user account uses S-1-0 with 4-part sub-authorities.

Legitimate uses of S-1-0-0 = "Nobody" (well-known null SID, ZERO sub-authorities).
These SIDs (S-1-0 with FOUR large random-looking sub-authorities) do NOT exist
in any Microsoft SID scheme. They are fabricated identifiers.

The sub-authority values appear pseudo-random:
  113147267-1519095794-715387272-2850185809
  1650355308-2408325621-503012698-2937194152
  3460105017-2885499184-3102270867-2206445538
  130827018-994964869-2702941970-2332722214
  4169528122-3105903461-1535511230-882767497

Pattern: 5 different SIDs used across 5 attacks — each attack uses a fresh SID.
This is deliberate evasion: rotating the SID means no single IOC can block all
instances. The attacker generates unique fake SIDs per attack cycle.

The entity owning these SIDs could be:
  - A process running under an injected/custom token with fabricated SID
  - A kernel-level component that generates its own SID for token access
  - A remote process accessing the token during the 47-92ms window

=============================================================================
ACCESS RIGHTS BREAKDOWN (DACL ACE FLAGS)
=============================================================================

GA  = GENERIC_ALL  (0x10000000) — full access, can do anything to the token
RC  = READ_CONTROL (0x00020000) — read security descriptor only
GXGR = GENERIC_EXECUTE|GENERIC_READ — can use/query token, cannot modify

Original DACL (pre-attack):
  lloyd:     GA   — owner has full control
  SYSTEM:    GA   — kernel has full control
  SessionID: GXGR — current logon session can execute/read the token

Post-injection DACL (during 47-129ms window):
  S-1-0-xxx: GA   — *** ghost entity has FULL CONTROL ***
  Owner:     RC   — owner demoted to read-only (cannot modify token)
  lloyd:     GA   — user SID preserved
  SYSTEM:    GA   — SYSTEM preserved
  [SessionID REMOVED]

Post-cleanup DACL:
  lloyd:     GA
  SYSTEM:    GA
  [SessionID still removed — PERMANENT side effect of the attack]

The permanent removal of the logon session SID from the token DACL means
lloyd's session can no longer properly assert read/execute rights on its own
tokens through the normal S-1-5-5-0-SESSION mechanism. This is a persistent
modification even after the ghost SID window closes.
